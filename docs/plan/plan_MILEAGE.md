# План MILEAGE: пробег авто не больше 400 000 км, иначе решение review

Источник: задача дня 1 (`docs/README.md`), карта кода `docs/setup/code_map.md:42–66`.
Правило — понижение решения, а не запрет: пробег > 400 000 при `approve` → `review`.

## 1. Файлы

- `backend/config/rules.php` — добавить ключ `vehicle.review_mileage_km => 400000` (не трогая `max_mileage_km` = 500 000).
- `backend/src/Domain/AssessmentService.php` — новый параметр конструктора `int $reviewMileageKm` и блок понижения решения после строки 33 (`$decision = $this->decisionEngine->decide($ltv);`).
- `backend/src/AppFactory.php` — передать `$rules['vehicle']['review_mileage_km']` в конструктор `AssessmentService` (строки 30–39).
- `tests/Unit/AssessmentServiceTest.php` — фикстура `payload()` получает пробег параметром; новые тесты границ и пустого пробега; существующие три теста остаются зелёными (у них пробег 96 000 — ниже порога).
- `docs/setup/code_map.md` — после реализации обновить раздел «Правило "пробег > 400 000 км → review"» (из «куда встанет» в «как устроено»).

Не меняются: `ApplicationValidator` (валидация 0…500 000 остаётся), `DecisionEngine` (сигнатура `decide(float $ltv): string` и докблок «решение на основании LTV» сохраняются), `LtvCalculator`, `ApplicationRepository`, `db/schema.sql`, фронтенд.

## 2. Шаги реализации

1. `rules.php`: в секцию `vehicle` добавить `'review_mileage_km' => 400000` с комментарием о семантике (порог понижения решения, не валидации).
2. `AssessmentService`: добавить `private readonly int $reviewMileageKm` в конструктор (последним параметром).
3. `AssessmentService::assess()`: после строки 33 —

   ```php
   if ($input['mileage'] > $this->reviewMileageKm && $decision === DecisionEngine::APPROVE) {
       $decision = DecisionEngine::REVIEW;
   }
   ```

   Условие `=== APPROVE` обязательно: `review` не повышается, `reject` не смягчается. `approved_limit` (строка 39) станет 0 автоматически.
4. `AppFactory::create()`: передать `$rules['vehicle']['review_mileage_km']` в `AssessmentService`.
5. Обновить тесты (раздел 3), прогнать `make test` и `make lint`.
6. Обновить `docs/setup/code_map.md`.

Порог из конфига приходит только в `AssessmentService`; `ApplicationValidator` продолжает читать только `max_mileage_km`.

## 3. Тесты

Новые тесты в `AssessmentServiceTest` (пробег — параметр `payload()`; LTV фиксированно низкий, например 450 000 / 900 000 = 50 %, чтобы без правила было бы `approve`):

- 399 999 км → `decision === approve`, `approved_limit === 450000`.
- 400 000 км → `approve` (порог «не больше», понижение строго `>`).
- 400 001 км → `review`, `approved_limit === 0`.
- Пустой пробег (нет ключа `mileage`) → `ValidationException` от валидатора, до LTV дело не доходит; тест на существующее поведение, чтобы подтвердить, что новое правило его не меняет.

Дополнительно (по желанию): 400 001 км при высоком LTV → остаётся `reject` (понижение не смягчает reject); 400 001 км при среднем LTV → остаётся `review`.

Регресс: три существующих теста (`approve`/`review`/`reject` при 96 000 км) должны проходить без правок.

## 4. Риски

- **Существующая проверка `max_mileage_km`**: границы 0…500 000 остаются в `ApplicationValidator`. Пробег > 500 000 не дойдёт до правила (ValidationException), т. е. понижение реально работает только в диапазоне 400 001…500 000. Если заказчик ждёт «иначе review» и для большего пробега — это отдельное решение (см. вопросы).
- **Смена сигнатуры конструктора `AssessmentService`**: все места сборки (прод `AppFactory`, тесты `AssessmentServiceTest`, возможно, Feature-тесты) должны получить новый параметр; пропуск даст TypeError, а не тихую ошибку — но места сборки нужно найти все.
- **`review` не превращается в `reject`**: если бизнес позже захочет не понижение, а отказ — это уже другое правило; текущий план делает ровно понижение `approve → review`.
- **Расхождение комментария и кода в LTV-границе** (`code_map.md:40`, `<` против `<=`): не входит в задачу, но при тестах на границах легко перепутать — тесты MILEAGE фиксируют только поведение пробега.
- **Ключ в конфиге**: если назвать порог `max_mileage_km` вместо нового ключа — сломается валидация; семантику ключей нельзя смешивать.

Не входит: пересчёт `approved_limit` по `ltv_by_age` (задача LOAN-12), сверка пробега по VIN с внешним справочником (CASE-08), фронтенд (только вывод решения), хранение в БД (пробег уже сохраняется как есть).

## Вопросы к заказчику

1. Пробег ровно 400 000 — `approve` или `review`? В плане принято «не больше 400 000 → approve» (строго `>` понижает).
2. Пробег > 500 000 (за пределами валидации) — оставить ValidationException или расширить диапазон и тоже давать `review`?
3. Порог «иначе review» — понижение только `approve → review`, или `reject` при большом пробеге тоже должен меняться?
4. Пробег свыше порога должен где-то отражаться в ответе отдельно (флаг/причина), или достаточно изменения `decision` и `approved_limit = 0`?
5. Фронтенду нужно как-то подсвечивать причину «пробег», или у него нет обратной связи по решению?
